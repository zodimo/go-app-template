## Context

The repository is a Go CLI starter template whose mechanical plumbing (cobra routing, viper config, slog+lumberjack logging, SQLite+golang-migrate) is genuinely reusable, but whose identity is hardcoded as `go-cli` / `GOCLI` / `github.com/zodimo` across ~35 files. The README lists a `--cwd` flag and a "MakeFile" that do not exist, and the tree contains committed machine-local artifacts (`go-cli-config.json`, `.go-cli/`, test panic logs). There is no git history yet.

The consumer contract (from the exploration) is "**B + C**": a repeatable scaffold where a stranger's clone becomes a working, renamed app deterministically, and the template is public-facing. Reference implementation studied: `golang.org/x/tools/cmd/gonew` (AST-aware module + import rewriting via `go/parser`/`modfile`).

## Goals / Non-Goals

**Goals:**
- Make app identity **runtime-driven from a single source** rather than scattered hardcoded literals.
- Provide an embedded `setup` cobra command that interactively re-identifies a cloned project, idempotently and non-destructively.
- Document the gonew-based clone flow so `fork → renamed app → build` is deterministic.
- Ensure no machine-local or generated runtime artifacts are ever committed.
- Fix the bug/stub debt surfaced during exploration (`--cwd`, panic-tag copy-paste, `fmt.Println` in `root.go`, dead `Execute()`/`--json` path, skeleton README).

**Non-Goals:**
- Not collapsing the three binaries into one (the `cli` / `cli-config` / `cli-migration` split is a deliberate, preserved pattern).
- Not replacing or vendoring `github.com/zodimo/go-maybe` — it stays an external, documented dependency.
- Not adding TUI prompt libraries — prompts are stdlib-only.
- Not implementing the full one-shot "clone everything for me" tool; gonew covers the module layer, the wizard covers identity.
- Not deciding the eventual module-publish/versioning/tagging cadence here (flagged as a follow-up).

## Decisions

### D1 — Identity single-source: `internal/identity/identity.go` (B2a)

Introduce a wizard-generated Go file as the one home for application identity:

```go
// internal/identity/identity.go  (generated by `setup`)
package identity

var (
    AppName    = "myapp"        // human/app name
    ConfigName = "myapp-config" // config file base name
    EnvPrefix  = "MYAPP"        // environment variable prefix
    DataDir    = ".myapp"       // runtime data directory
    BinTrio    = "myapp"        // binary prefix: myapp, myapp-config, myapp-migration
)
```

All consumers (`config.go` constants, viper env prefix, search paths, log/db filenames, gitignore entries) read from these instead of hardcoding `go-cli`/`GOCLI`/`.go-cli`.

**Alternatives considered:**
- *B2b (ldflags/env injection)*: identity would flow via `go build -ldflags "-X ..."`. More flexible but adds build-tooling indirection that obscures a beginner-facing template's reading. Rejected for C audience clarity.
- *B1 (bake at fork via find-and-replace)*: one-shot, destructive, and re-renaming is manual again. Rejected in favor of runtime single-source.

Rationale: B2a keeps the code obvious (read `identity.AppName`), makes rebuild trivial (`go build ./...` just works after the wizard writes the file), and delivers the B2 payoff — rename is always non-destructive (edit one file or re-run `setup`).

### D2 — Clone flow: gonew for Layer 1, `setup` for Layer 2

Documented consumer flow:

```
1. gonew github.com/you/go-app-template@vX.Y.Z your.domain/myapp
     → AST-aware copy; rewrites go.mod module + all internal imports
2. myapp setup                        ← our wizard (cobra command)
     → collects AppName / EnvPrefix / DataDir
     → writes internal/identity/identity.go
     → renames cmd/cli → cmd/myapp, cmd/cli-config → cmd/myapp-config, etc.
     → rewrites cobra Use:, panic tags, gitignore
3. go build ./...                       → working, renamed app
4. myapp-config init                    → generates config (never shipped)
```

gonew only rewrites `.go` files + `go.mod` (verified in `cmd/gonew/main.go`: `fixGo` + `fixGoMod`). It intentionally leaves app identity, cmd dirs, cobra names, gitignore, and filenames alone — exactly what our `setup` command must handle. Hence two complementary layers.

### D3 — `setup` is a cobra command, stdlib prompts

`setup` ships inside the app as a real cobra command (not a standalone tool), invoked as `<app> setup`. Prompting uses `fmt.Print` + `bufio.Scanner` / `golang.org/x/term` if needed — no survey/bubbletea. Keeps `go.mod` lean and the pattern teachable.

The wizard performs a **file rename + in-place rewrite** pass over:
- `internal/identity/identity.go` (generate new content)
- `cmd/cli`, `cmd/cli-config`, `cmd/cli-migration` directory names → `BinTrio` variants
- cobra `Use:` strings in the three `*/commands/root.go`
- panic-recovery tags in `cmd/*/main.go`
- `.gitignore` entries (`/go-cli-config.json` → `/myapp-config.json`, `/.go-cli` → `/.myapp`)

It must be **idempotent**: re-running with the same values is a no-op; running again with new values re-identifies the whole tree consistently. Guard against partial states by validating input before writing.

### D4 — Template hygiene (Layer 3)

- Add to `.gitignore`: `go-cli-config.json` (→ generated name), `.go-cli/` (→ generated name), `*.log`, `.env`.
- Delete committed `go-cli-config.json`, `.go-cli/`, and `internal/logging/logging.test-panic-*.log`.
- Config is produced by `config init` on first run, never shipped.
- Filesystem locations derive from `identity.*` (absolute paths come from `os.Getwd()`/config at load, never hardcoded).

### D5 — Bug/stub debt fixes (small, independent)

- **BREAKING** none; additive.
- Wire a real `--cwd` persistent flag (README already documents it) and have `config.Init` honor it (the plumbing that reads `cwdFlag` already exists in `internal/config/init.go`).
- Fix `cmd/cli-migration/main.go` to use `RecoverPanic("cli-migration-main", nil)` instead of the copied `"cli-config-main"`.
- Remove stray `fmt.Println(err)` in `internal/commands/root.go` PersistentPreRunE.
- Reconcile the `main()` path: `cmd/cli/main.go` executes `RootCmd.Execute()` directly and bypasses `commands.Execute()` (which feeds `--json` error output). Decide a single error/`--json` path.
- Fill README sections; add `Makefile` matching the documented target surface (build / test / config init / migrate).

## Risks / Trade-offs

- [Wizard must not corrupt the tree] → Mitigation: validate all inputs up front; only mutate after successful interactive collection; keep renames idempotent (guard against already-renamed state); leave a `--dry-run` that prints planned changes without applying.
- [Identify *all* hardcoded literal sites] → A missed literal (e.g. in a test or comment) leaves residual `go-cli` branding. Mitigation: exhaustive grep of `go-cli` / `GOCLI` / `go-cli-config` / `.go-cli` / `cli-migration` / `cli-config` during implementation and a final sanity check that no literal remains outside the identity source.
- [Module path must be versioned for gonew @version flow] → Template must be published + git-tagged. This is a process follow-up; `setup` still works on a plain `git clone` (identity is independent of module path).
- [Test churn] → `internal/config/load_test.go` asserts `GOCLI_DATABASE_DATABASE`. When env prefix is parameterized, tests must read from the identity source or the wizard must not parameterize test fixtures. Decide: tests use `identity.EnvPrefix` so they stay valid after re-identity.
- [Rename of cmd dirs breaks import paths] → `cmd/*/main.go` import `github.com/.../internal/commands`. Directory rename inside `cmd/` does not change those internal import paths (they are package-internal), but cobra `Use:` and any `go:generate`/doc references must be updated together. Mitigation: wizard updates all references atomically.
- [go-maybe stays external] → A fork depends on `github.com/zodimo/go-maybe` remaining available. Accepted by decision; documented in README as a required dependency.

## Migration Plan

1. Land identity single-source (`internal/identity`) and refactor `config.go`/`viper.go`/`init.go` to read from it — behavior preserved, `go-cli` values become the template defaults.
2. Add `setup` command + wizard logic (write identity, rename cmd dirs/Use/tags/gitignore).
3. Apply template hygiene (gitignore, delete artifacts).
4. Apply bug/stub fixes (`--cwd`, panic tag, `fmt.Println`, `Execute()`/`--json`).
5. Fill README + add Makefile; document gonew + `setup` flow.
6. (Follow-up, not in scope) Tag + publish module so `gonew ...@version` resolves.

Rollback: because identity moves to a single generated file, reverting = restoring `internal/identity` default and git-ignoring the generated state. `setup` is non-destructive and re-runnable, so a bad re-identity is correctable without reset.

## Open Questions

- Q1: Should `setup` be a top-level command even before the app is renamed (i.e. `cli setup`), or only meaningful as `<renamed-app> setup`? Leaning: always registered on all three binaries via the shared `commands` wiring, so it's available regardless.
- Q2: For test fixtures asserting `GOCLI_...` — parameterize via `identity.EnvPrefix` or leave fixture literals? Leaning: parameterize so re-identity doesn't break tests.
- Q3: Should the README "MakeFile" target a real committed `Makefile` (recommended) or just document `go build`/`go run`? Leaning: add a minimal real `Makefile`.
